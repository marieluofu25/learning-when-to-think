§ 0

Abstract

Large language models allocate a fixed amount of computation to every input regardless of difficulty. Simple problems receive unnecessary reasoning chains; hard problems may not receive enough exploration. This fixed-compute paradigm wastes resources and limits accuracy.

Test-time compute is a growing bottleneck in deployed LLM systems. As models scale, the ability to adaptively route computational effort — more for hard problems, less for easy ones — directly impacts both cost and accuracy at inference time.

We formulate reasoning as a sequential decision-making problem where the model acts as an RL agent choosing among actions: continue, verify, sample alternative, call tool, or terminate. A reward function balancing correctness against computational cost trains the policy via PPO or GRPO with LoRA fine-tuning.

We evaluate on GSM8K (mathematical reasoning) and HumanEval (code generation), comparing the adaptive policy against chain-of-thought, self-consistency, and greedy decoding baselines. Primary metrics are task accuracy and reasoning tokens per correct answer.

§ 1

Introduction

Modern large language models achieve impressive performance on reasoning tasks through test-time computation techniques such as chain-of-thought (CoT) prompting and self-consistency sampling. However, these approaches suffer from a fundamental inefficiency: they apply a fixed computational budget uniformly across all inputs. A simple arithmetic question receives the same extended chain-of-thought as a graduate-level proof problem.

"The optimal amount of reasoning effort is a property of the problem, not of the model — yet current systems have no mechanism to learn this distinction."

This mismatch has concrete costs. Unnecessary reasoning tokens increase latency and API expense. Conversely, prematurely terminating reasoning on hard problems produces incorrect answers. The question we investigate is: can reinforcement learning teach an LLM to decide, at each step, how much further to think?

We extend this question to include tool use as a first-class reasoning action. Rather than forcing the model to compute arithmetic symbolically through language tokens, we allow it to call a Python executor and inject the result back into the reasoning trace. This mirrors how humans naturally switch between mental arithmetic and reaching for a calculator.

This problem is directly relevant to the course's focus on reinforcement learning for sequential decision making. The reasoning process maps cleanly onto the MDP framework: states are accumulated reasoning traces, actions are reasoning operations, and rewards encode the accuracy–efficiency trade-off. Solving it requires both careful reward shaping and policy optimization — core topics covered in the course.

Our work sits at the intersection of test-time compute scaling, reinforcement learning for LLMs, and tool-augmented reasoning. We compare and contrast our approach with the following lines of work.

Wang et al., ICLR 2023
Samples multiple CoT paths and takes a majority vote. This is one of our primary baselines. Self-consistency applies fixed over-sampling; our method learns to sample an alternative only when early evidence suggests the current path is failing, reducing wasted computation.

Schulman et al., arXiv 2017
Provides the foundational policy optimization algorithm we use. Enables fine-tuning of large models by injecting trainable low-rank matrices into transformer layers, keeping the base model frozen. We use LoRA as our fine-tuning strategy, making RL training computationally feasible on free-tier GPU resources available via Hugging Face and Colab.

§ 3

Method

Core Insight

We frame LLM reasoning as a Markov Decision Process. At each step, the model observes its accumulated reasoning trace (state) and selects from a discrete set of reasoning actions. A scalar reward, received at episode termination, encodes the trade-off between getting the right answer and the computational cost incurred to get there.

The key insight is that the reasoning action itself should be a learnable decision, not a fixed heuristic. Rather than always generating more tokens (CoT) or always stopping early (greedy), the policy learns a context-sensitive allocation strategy — including knowing when to delegate numerical computation to a Python executor rather than approximating it in natural language.

MDP Formulation

We define the MDP as follows: the state st is the concatenation of the problem prompt and all tokens generated so far (the reasoning trace). The action space A contains five discrete actions:

Action Description When beneficial
CONTINUE Generate the next reasoning step via CoT Problem requires multi-step logical decomposition
VERIFY Re-check the most recent intermediate result After a computation-heavy step; when confidence is low
SAMPLE ALT Restart with a different solution path When the current path appears stuck or contradictory
CALL TOOL ★ Generate Python code, run executor, inject result Arithmetic-heavy sub-problems; numerical computation
TERMINATE Emit the final answer and end the episode When answer confidence is high; simple problems
Reward Function

The reward is received only at episode termination (sparse reward). It balances three terms:

Reward Function
R = rcorrect − λ · |tokens| − μ · |tool_calls|

Where rcorrect ∈ {0, 1} is the answer correctness indicator, |tokens| is the total reasoning trace length, and |tool_calls| is the number of Python executor invocations. The hyperparameters λ and μ control the accuracy–efficiency trade-off and the tool-use penalty respectively. The policy learns that tool calls are expensive but can be worth it — enabling emergent adaptive tool selection based on problem type.

Training Algorithm

We fine-tune the base LLM using LoRA adapters, keeping all original weights frozen. Policy optimization is performed with PPO (primary) and GRPO (ablation). For GRPO, we sample a group of trajectories per problem and use relative rewards within the group to reduce variance without a separate value network. The action-selection head is implemented as a lightweight classifier over the LLM's hidden state at the end of each generation step.

Implementation Stack

We use the Hugging Face trl library (PPO/GRPO trainers), peft for LoRA management, and bitsandbytes for 4-bit quantization. The Python executor is implemented as a sandboxed subprocess with a 5-second timeout, returning stdout or a traceback as a string token that is appended to the reasoning trace. Training runs on a single Colab A100 (40GB) or two T4s with model parallelism.

System Workflows

The system operates in two distinct phases with different data flows, objectives, and behaviors. Training updates policy weights via gradient descent; inference deploys frozen weights and measures task performance.

Training workflow
Inference / testing workflow

At inference time, the trained policy runs deterministically (greedy or low-temperature sampling). No gradient updates occur. We measure task accuracy and token efficiency independently on the held-out test sets, then compare against three baselines: standard chain-of-thought, self-consistency (majority vote over 10 samples), and greedy decoding.

§ 6

Experimental Design

Testable Hypotheses
H1
Adaptive Compute
An RL-trained adaptive policy achieves equal or higher accuracy than standard chain-of-thought on GSM8K while using fewer reasoning tokens on average, demonstrating that the policy learns to skip unnecessary computation on simple problems.
H2
Tool Use Specialization
When the call_tool action is available, the policy learns to invoke the Python executor more frequently on arithmetic-heavy sub-problems and less frequently on symbolic/logical reasoning, without being explicitly supervised to do so — emerging purely from reward signal.
H3
Efficiency–Accuracy Trade-off
Varying the penalty coefficient λ (token cost) traces a Pareto frontier between task accuracy and compute efficiency, and the adaptive policy dominates the self-consistency baseline on this frontier — i.e., for any target accuracy level, the adaptive policy requires fewer tokens.
Experiment Plan

Evaluation Criteria

Primary: Task accuracy on held-out test sets (exact match for GSM8K; pass@1 for HumanEval). A result confirms H1 if the adaptive policy achieves within 2 percentage points of the CoT baseline while reducing average token count by ≥ 20%.

Secondary: Compute-per-correct-answer (total tokens consumed divided by number of correct answers). A result confirms H3 if the adaptive policy's Pareto curve dominates self-consistency at the same accuracy operating point.

Qualitative: Action-trace analysis — we will sample 50 problems per benchmark and manually inspect the action sequences chosen by the trained policy to verify that tool-use patterns are semantically sensible (H2).
