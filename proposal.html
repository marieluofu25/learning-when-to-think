Learning When to Think: RL for Adaptive Reasoning Computation in LLMs

Ivan Andhika · u1590903 Hao Ren · u1527543 Ammon Gleason · u1221580
University of Utah · GSM8K & HumanEval · PPO / GRPO + LoRA
00

Abstract

What is the problem?

Large language models allocate a fixed amount of reasoning computation for every input regardless of difficulty. Simple problems are over-processed; hard problems may terminate before sufficient exploration.

Why does it matter?

Inference compute is expensive. A model that wastes tokens on trivial problems or gives up too early on hard ones is both inefficient and inaccurate — a critical limitation for real-world deployment at scale.

Proposed solution

We formulate reasoning as a sequential decision-making problem. An RL policy (PPO/GRPO) trained with LoRA learns to select from five actions — continue, verify, sample alternative, call tool, or terminate — based on problem difficulty signals.

Planned experiments

We compare our adaptive policy against fixed-compute baselines (standard CoT, self-consistency) on GSM8K and HumanEval, measuring task accuracy, token usage, and compute-per-correct-answer.

01

Introduction

Modern large language models have demonstrated impressive reasoning capabilities, largely attributed to test-time computation strategies such as chain-of-thought (CoT) prompting, self-consistency sampling, and process-reward-guided search. However, a persistent inefficiency underlies these approaches: the amount of computation allocated to each problem is fixed at design time rather than determined by the problem itself.

Consider two inputs: "What is 7 × 8?" and "A train leaves Chicago at 9am traveling 60 mph...". Current systems would allocate the same reasoning budget to both. This is analogous to a student spending equal time on every exam question — clearly suboptimal. The student who has internalized when to think carefully outperforms one who always thinks the same amount.

We investigate whether reinforcement learning can teach an LLM exactly this skill. We frame reasoning as a sequential decision-making problem in which the model acts as an RL agent, choosing from a discrete action space at each step: continue the chain-of-thought, verify an intermediate result, sample an alternative solution path, invoke a Python executor for computationally intensive sub-problems, or terminate and return the answer.

This problem is directly relevant to this course's core themes of reinforcement learning, policy optimization, and sequential decision-making. It applies RL not to a game environment but to the internal reasoning of a language model — a novel and practically significant domain where reward signals (answer correctness, token cost) are naturally defined and the policy space is rich and structured.

03

Method

Key insight: reasoning is not a fixed-length monologue — it is a sequential decision process. Teaching a model when to stop, when to check, and when to delegate to a tool is strictly more powerful than teaching it to reason longer.

We formulate the reasoning process as a Markov Decision Process (MDP). The state at step t is the concatenation of the problem and all tokens generated so far (the reasoning trace). The action space A consists of five discrete meta-actions:

ActionMechanismWhen preferred
CONTINUEGenerate next CoT tokensProblem requires more logical steps
VERIFYRe-evaluate last intermediate resultUncertain intermediate; high-stakes step
SAMPLE_ALTRestart with different approachCurrent CoT path appears stuck
CALL_TOOLNEWExecute Python code; inject resultArithmetic-heavy subproblem where CoT is error-prone
TERMINATEReturn current answer as final outputConfident answer; further compute not worth it

The reward function jointly optimizes answer quality and computational efficiency:

R = rcorrect  −  λ · ntokens  −  μ · ntool_calls rcorrect = +1 if correct, 0 otherwise  ·  λ = token cost sensitivity  ·  μ = tool call overhead penalty

The policy is implemented as an instruction-tuned LLM with LoRA adapters. At each reasoning step, the model generates a special action token (e.g., [CONTINUE], [CALL_TOOL]) before generating content tokens, allowing the RL signal to directly update action selection probabilities. Training uses PPO or GRPO via the HuggingFace trl library. When CALL_TOOL is selected, the model generates a Python code snippet, the executor runs it, and the result is injected back into the trace as an observation token before the next step.

This design allows the policy to learn empirically: "For GSM8K arithmetic-heavy problems, CALL_TOOL reduces error and total token cost compared to multi-step CoT." The μ penalty prevents trivial solutions where the model spams tool calls for every step.

Experimental Design

Testable Hypotheses

H1
Accuracy–efficiency trade-off
An RL-trained adaptive reasoning policy achieves equal or higher accuracy than standard chain-of-thought prompting while using fewer total reasoning tokens.
Evaluation: Compare (accuracy, avg. tokens/problem) on GSM8K test set. Hypothesis confirmed if adaptive policy achieves ≥95% of CoT accuracy at ≤80% of CoT token budget.
H2
Tool use improves hard problem accuracy
Adding a CALL_TOOL action (Python executor) improves accuracy on arithmetically complex problems compared to a CoT-only policy with no tool access.
Evaluation: Subset GSM8K by difficulty tier. Measure accuracy delta between tool-augmented and CoT-only policy on hard problems (≥4 arithmetic operations required).
H3
Policy generalizes across domains
A policy trained on GSM8K maintains adaptive compute behavior when evaluated on HumanEval without domain-specific retraining.
Evaluation: Compare action frequency distributions on GSM8K vs. HumanEval. Significantly different distributions indicate the policy learned domain-aware reasoning allocation.

Domains & Datasets

GSM8K — Math Reasoning
Grade-school math word problems requiring sequential arithmetic and algebraic reasoning. Integer answers allow automatic reward computation without a verifier model.
8,500 train / 1,319 test problems
HumanEval — Code Generation
Python function completion from docstrings. Evaluated via unit test execution (binary correct/incorrect). Especially suited for CALL_TOOL since generated code can be directly executed as verification.
164 problems · pass@1 metric

Baselines

We compare against three fixed-compute baselines, all using the same base model without RL fine-tuning: (1) Standard CoT — greedy decoding with chain-of-thought prompting; (2) Self-consistency@8 — 8 sampled chains with majority vote; (3) Direct answer — no chain-of-thought at all. This three-point baseline clearly spans the compute spectrum and isolates the contribution of adaptive allocation.
